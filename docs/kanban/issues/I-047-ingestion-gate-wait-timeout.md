## Goal

给 `LocalIngestionDataSource` 的 `_ingestionGate.WaitAsync(ct)` 加**等待超时**（issue #1 报告者建议
30 分钟量级）：超时则记录日志并放弃本轮等待，让后续刷新可以重新进入——避免一次挂死的轮次
把定时刷新与手动刷新**永久**堵在门外。报告者原话："超时则记录日志并允许下一轮重新进入，
避免一次挂死永久失效"。

## Background

### 现状（已对照源码核实）

- `LocalIngestionDataSource.cs:280`：`await _ingestionGate.WaitAsync(ct)` **无超时**——
  `SemaphoreSlim` 用 `finally { Release(); }` 保证不泄漏（`LocalIngestionDataSource.cs:370`），
  但**持锁的那一轮若永不返回**（任何原因的挂死），后续所有轮次会在这里无限排队。
- 排队的上游是 `BackgroundRefreshService` 的合并槽（CAS 抢占 + `TCS` 等待）：
  定时 tick 各自并入在跑的一轮、不追加新轮。于是挂死轮存在期间，**每一轮新触发都只是换一个
  等待者**，应用表现为"刷新彻底失效且无任何报错"——issue #1 报告者实测第 142 秒跨过
  `RefreshMinutes: 5` 的 tick 后"没有任何新动作"，就是这个合并语义下 gate 挂死的直接后果。
- 手动刷新（⟳ 按钮 / 设置页重扫 / 托盘「立即刷新」）走同一 `TriggerRefreshAsync`，同样被堵。

### 触发事件

- issue #1 顺带改进 #2。根因（去重器二次方退化）已由 PR #2 修复，但**结构性的"无超时 gate +
  无界合并"组合仍在**：任何未来的单轮挂死（新的运行时 bug、文件系统异常、第三方适配器死循环）
  都会复现"一次挂死 → 刷新永久失效"。超时是廉价的最后一道防线，不依赖根因清零。

## 定案方向（实现时确认）

1. **超时只加在等待上，不强杀在跑轮次**：`WaitAsync(TimeSpan, ct)` 超时后本轮如实放弃
   （返回什么由调用方语义决定——`GetDailyUsageAsync` 返回空列表 + 状态上报，
   保证 UI 不误显错误数据），**绝不中断仍持有 gate 的那一轮**（强杀会把增量扫描器实例
   留在任意中间态，单例适配器非线程安全，下一次进入直接踩坏——这是明确不做的部分）。
2. **超时时长**：报告者建议 30 分钟。取值原则 = 必须远大于最慢合法轮
   （16k 文件 × 二次方问题修复后的解析 + 去重 + 落库），远小于"用户当天还会再看一眼"的尺度；
   具体值实现时定，做成常量并注释取值依据。
3. **可观测性**：超时放弃时经 I-045 的文件日志记录（含已等待时长）；若 I-045 未先行落地，
   先走 `Console.Error`（保留现状通道），I-045 落地后切换。
4. **上层联动**：`BackgroundRefreshService` 的合并等待者拿到放弃结果后按现有失败路径上报
   （状态灯 error），不重试风暴——定时器下一 tick 自然再试，天然退避。
5. **卡内明确不做**：不给 gate 排队人数设上限、不做"检测挂死并 abort 线程"（.NET 无安全abort）、
   不改 `BackgroundRefreshService` 的合并语义本身。

## Acceptance Criteria

- [ ] gate 被长期占住（fixture 用不释放的 `SemaphoreSlim`）时，等待方在超时后返回，
      状态按"本轮放弃"如实上报，**进程不崩、后续轮次可重新进入 gate**
- [ ] gate 正常释放路径零变化：既有全量测试（含并发刷新用例）零改动通过
- [ ] 超时事件有日志/诊断输出（I-045 已落地则写文件日志）
- [ ] 取消令牌取消仍即时生效（`ct` 与超时并存语义正确）
- [ ] 全量测试 0 失败

## 开放问题

- 超时放弃轮在 UI 上的呈现口径：沿用状态灯 error（"本轮放弃"与"扫描失败"同色不同文案？）
  还是复用 no data？——实现时与 S-002 的状态语义对齐，勿造第三种状态色。
- `IsScanUnchanged` / 强全量旗标（`_forceFullNextRound`）与放弃轮的交互：放弃轮不得清除旗标
  （旗标只在全量管道成功后清除，现有语义已正确，需测试锁住）。
